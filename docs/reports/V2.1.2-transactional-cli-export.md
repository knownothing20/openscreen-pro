# V2.1.2 — CLI 事务式导出与数据安全收尾

起点：`4c502e212450532d384fde644c13b007904cbe68`（V2.1.1 final）
范围：把「原生渲染 → 配音混音 → 落盘」改成一个事务，只有全部阶段成功才替换用户的目标文件。
**本轮没有修改 Rust**（沿用 V2.1.1 的 `37a77a80…` addon，未重新编译）。

## 2. 新旧导出流程

**旧（缺陷）**

```
outPath ──► 原生编码直接写入（temp→rename 到 outPath）
              │
              ├─ 读 outPath + 配音 ─► 混音 ─► 写回 outPath
              │                                   ▲
              └─ 任一阶段失败 ────────────────────┘ 目标已被第一阶段的产物顶掉
```

**新（事务）**

```
preflight(outPath, 保护名单)        ← 编码前拒绝，1.3s 而不是 12s
        │
render ─► <base>.render-<token>.mp4   ← 原生编码，绝不碰 outPath
        │
读回并校验 MP4（ftyp + moov）
        │
   ┌────┴──── 无配音 ────────────────┐
   │                                  │
有配音：读配音 → 混音 → 写 <base>.mixed-<token>.mp4 → 校验 MP4
   │                                  │
   └────────────► commit(stage → outPath)  ← 唯一能改变用户文件的一行（rename）
                                     │
                     finally: 删除两个 stage（无论成功失败）
```

无配音时不额外转码、不额外读一遍：渲染出的 stage 直接提交。

## 4. 事务与临时文件机制

- 阶段名：`<stem>.render-<token>.mp4` / `<stem>.mixed-<token>.mp4`，**与目标同目录**（rename 不能跨卷），
  token 默认 `时间戳36 + 随机 8 位`，每次调用都新生成 ⇒ 并发任务不会共享阶段文件（单元测试连出 50 个名字全不同）。
- 扩展名保持 `.mp4`，muxer 与 `ffprobe` 都认。
- 阶段名只有本应用会产生：`isExportStageName` 的同一份正则同时用于**提交拒绝**、**重命名校验**和
  **清理 IPC 的白名单**——渲染进程无法借"清理"删掉任意路径。
- 清理：`finally` 中对已产生过内容的 stage 逐个 `delete-export-stage`（best-effort，失败只 warn）。
  成功提交后 stage 已被 rename 走，删除是空操作。
- 参考：原生侧仍用 V2.1.1 的 `.partial-<pid>-<uuid>` 内部临时文件，与本轮 stage 是两层不同职责的文件。

## 5. 原子提交实现（在真实 Windows 上量过，不是按函数名推断）

`commit-export-file` → `planExportCommit` → `commitExportFile`（V2.1.1 已验证过的那一个）。

实测 `fs.rename` 在 Windows 上的四种语义（Node 22，NTFS）：

| 情形 | 结果 |
|---|---|
| 目标存在 | **被替换**，stage 消失（`NEW` 生效） |
| 目标正在被本进程打开 | **EPERM 拒绝**，旧文件不动 ⇒ 用户开着播放器时提交失败但数据安全 |
| 目标是目录 | **EPERM 拒绝**，stage 保留（本轮用它做"提交失败"注入） |
| 跨卷 | **EXDEV** ⇒ 所以 `planExportCommit` 要求 stage 与目标同目录 |

提交前还有两道门：目标必须是绝对路径 + `.mp4/.gif` + 不是本次运行的输入文件（`checkExportTarget`，
realpath + `dev:ino` 判同一文件）；stage 必须存在且非空（空则拒绝，目标不动）。

## 11. macOS / Linux 轻量兼容检查

只做了静态检查，**未编译、未运行**（本机无这两套环境）。

| 检查项 | 结论 |
|---|---|
| 共享 TS 是否有平台路径假设 | `stagePathsFor` 不依赖 `node:path`：同时认 `/` 与 `\` 作分隔符，其余纯字符串处理 ⇒ 两端都能用。**已知偏差**：POSIX 上文件名可以合法包含 `\`，会被误判为分隔符——属于极罕见文件名，记录不修 |
| 大小写 | `comparisonKey` 统一小写：Windows/macOS 默认卷正确；**Linux 大小写敏感**时，仅大小写不同的两个路径不会被判同一文件（假阴性方向，不会误删） |
| 取消接口签名 | 三平台一致：`pipeline_{windows,macos,linux}.rs` 均为 `cancel: Option<&dyn Fn() -> bool>`（本轮未改 Rust） |
| rename 语义 | 提交是同一目录内的 rename：POSIX 上原子替换；Windows 上已实测（§5）。EXDEV 由"必须在同目录"这条规则提前排除 |
| 新增代码是否引入 Windows 专属依赖 | 无：`exportTransaction.ts` 只有字符串处理与数组；主进程侧用 `fs.rm` / `fs.rename` / `path`，都是跨平台的 |
| 已有 CI/编译环境 | 无可用环境，**没有验证**——如实记为未验证 |

## 14. 未解决问题

1. **CLI 没有取消入口**（G/P 在 CLI 上 NOT_RUN）：`openscreen export` 是"跑完就退出"的一次性进程，
   没有信号/端口接收取消。本轮没有为此新增进程级信号系统（超出"最小"范围）。GUI 取消沿用 V2.1.1
   的实测结论（153 ms 停止、旧文件不变、可立即重导），且本轮没有改动那条路径。
2. **macOS / Linux 未编译验证**：见 §11，静态检查通过但无运行证据。
3. **CLI 失败时仍会留下"未混音的新导出"这一路径已关闭**；但**成功**覆盖时，目标文件会从旧字节
   直接变成新字节（这是想要的）。若用户想保留旧成片，需要 V2.2 的"导出历史/备份"能力。
4. **结构校验而非完整解码校验**：`isMp4` 只验 `ftyp` + `moov`，能挡住截断文件，但不保证每一帧可解。
   真正的可解码性由混音阶段（WebCodecs 解析整条视频轨）与后置 ffprobe 验收覆盖。
