## 3. 任务 A：30 分钟 H.265 完整验收

命令（CLI 与 GUI 读同一份 `recording-settings.json`，所以设备/格式的选择和用户在设置里选的是同一个）：

```
npx electron . export <v24_30min.openscreen> -o v25/a-30min-h265.mp4 --codec hevc --json
```

### 3.1 编码器实测

```
[pipeline] encodeur vidéo : hevc_nvenc (textures D3D11, zéro-copie)
```

设备：`id:PCI\VEN_10DE&DEV_2705&SUBSYS_413C1458&REV_A1\4&25C6DA53&0&0009`（RTX 4070 Ti SUPER 的 PnP 实例 ID，
不是 LUID）。**没有发生降级**：日志里没有 `fallback`，没有 `h264_amf`/`h264_nvenc` 被打开，
也没有 CPU 编码器参与。

### 3.2 产物核对

| 项 | 值 |
|---|---|
| 输出 | `v25/a-30min-h265.mp4`，544,634,918 B |
| 视频 | `hevc` / **`hvc1`** / Main / 1598×1080 / 60 fps / **108,000 帧** / 1799.983 s |
| 音频 | `aac` LC / 48 kHz / 2 ch / 1800.000 s / 84,376 帧 |
| 容器 | 1800.000 s，平均码率 2,420,599 b/s |
| 导出耗时 | **316.5 s**（`elapsed_ms=316527`） |
| 全片解码 | `ffmpeg -v error -i ... -f null -` → **退出码 0，stderr 0 行**，59.8 s |

对比 V2.4 的 30 分钟 H.264：619,457,152 B / 288 s ⇒ H.265 小 **12.1%**，慢 9.9%（这一条与 V2.3 在
42 秒工程上"HEVC 更小、速度基本持平"的结论方向一致，但长视频上 NVENC 的 HEVC 确实略慢）。

> 一处如实记录：日志里两条 `hevc_nvenc: option bitrate=… refusée (ret=-1414549496)` 是 **V2.4 就存在**
> 的既有现象（本机这版 FFmpeg 的 NVENC 封装不接受 `bitrate` AVOption），H.264 路径同样出现。
> 所以码率实际由 NVENC 的默认质量档决定，`--quality` 的 `bitrate` 字段在本机是无效参数。
> 本轮**没有动它**：它不影响正确性，且属于编码参数调优，不在这轮的"稳定性"范围内。

结论：**PASS**，并以"编码器名字 + 码流 tag + 帧数 + 全片解码"四项共同确认，而非"文件存在且非零"。

## 5. 任务 C：异常退出的残留文件

### 5.1 先审计：到底会留下什么

| 名字 | 谁写的 | 是否含 PID |
|---|---|---|
| `<stem>.render-<token>.mp4` | 事务式导出的第一阶段（CLI） | 否 |
| `<stem>.mixed-<token>.mp4` | 混音阶段（CLI） | 否 |
| `<stem>.partial-<pid36>-<nonce>.mp4` | `planExportWrite` → 原生编码器真正写入的文件（GUI 与 CLI 都经过它） | **是，base36** |
| `.openscreen-gif-<pid>-<nonce>.partial` | GIF 导出（Rust `gif_export_control.rs`） | **是，十进制** |

正常失败 / 取消路径由 `finally` 清干净（上面 §4 已实测 0 残留）。**只有进程被硬杀**（断电、
任务管理器、原生崩溃）才会把它们留在目标目录里。

### 5.2 清理规则（`electron/exportTempSweep.ts`，新文件 227 行）

四道闸门，缺一不可：

1. **文件名白名单**，四条精确正则（上面表格里的四种形态）。`holiday.mp4`、`demo.openscreen`、
   甚至 `demo.render-abcd.mp4`（token 太短）都**不是**候选。扩展名不参与判断。
2. **24 小时过期**（`DEFAULT_MAX_AGE_MS`）。一分钟前启动的导出留下的正是同名文件。
3. **PID 存活检查**（`process.kill(pid, 0)`）：名字里带 PID 的，进程还在就不动。
4. **本进程活跃登记**（`trackActiveExportTemp` / `activeExportTemps`）：stage 名字不带 PID，
   所以导出开始时把 `<stage>` 与 `<temp>` 都登记进去，并发的另一个导出不会被自己的清理误删。

其余边界：只扫**目标目录一层**（不递归）、只处理 `Dirent.isFile()` 为真的项（**符号链接和目录天然被跳过**）、
删除失败只 `console.warn`、目录不存在直接静默返回、任何异常都不外抛——它跑在真实导出的最前面，
**绝不允许把一次正常导出弄失败**。

挂载点三个：`compositor.exportMulti`、`compositor.exportGif`、`write-export-to-path`（CLI 混音阶段的写入），
都在写任何字节之前。

### 5.3 测试（先写失败测试）

`electron/exportTempSweep.test.ts`：16 条，15 通过 + 1 条在 Windows 上跳过（创建文件符号链接需要
`SeCreateSymbolicLinkPrivilege`，本机没有；守卫本身是 `entry.isFile()`，CI 的 Linux 会覆盖）。
覆盖任务书要求的全部九项，另外加了"不递归""目录不存在""幂等"。

**负向验证**（证明测试不是摆设）：

| 注入的缺陷 | 结果 |
|---|---|
| 去掉过期判断（`if (false && now - mtime < maxAge)`） | `keeps a file that has not expired` **失败**，其余 14 条仍过 |
| 去掉 PID 保护 | `keeps a partial whose pid is still alive` **失败** |

### 5.4 真实导出上的验证

在一个目录里布置 6 个文件（2 天前的 render / mixed / partial / gif-partial、刚生成的 render、用户自己的 `user-holiday.mp4`），
然后**真的导出一次**到该目录：

```
保留：fresh.render-cccccccc.mp4（未过期）、user-holiday.mp4（不是我们的）
删除：old.render-aaaaaaaa.mp4、old.mixed-bbbbbbbb.mp4、old.partial-1aao-deadbeef.mp4、
      .openscreen-gif-60000-abcd.partial
导出：exit 0，out.mp4 19,944,993 B
```

一条 `leftover temp file` 警告都没有——删得干净，且没有误伤。

**没有做的**：启动时扫描、后台常驻清理、跨目录递归、任何"恢复"机制。按任务书，宁可留着也不删。

## 6. 任务 D：长视频混音与内存

### 6.1 真实运行（10 分钟）

```
npx electron . export v24_10min.openscreen -o v25/d-10min-mix.mp4 --codec hevc --audio vo-10min.wav
```

| 项 | 值 |
|---|---|
| 耗时 | **128.2 s**（纯渲染同期约 99 s，混音段约 29 s） |
| 大小 | 201,562,724 B |
| 视频 | `hevc` / `hvc1` / 1598×1080 / 60 fps / **36,001 帧** / 600.000 s —— **编码未降级** |
| 音频 | `aac` LC / 48 k / 2 ch / 192,005 b/s / 600.021 s |
| 全片解码 | 退出码 0，stderr 0 行，19.7 s |
| 收尾 | 结束后 0 个 `.render-` / `.mixed-` / `.partial-` 残留 |

**音频内容核对**（不是"有音轨就算过"）：把输出的音轨和配音都解成 48 kHz 单声道 f32，
逐样本比对 60 秒：

```
best correlation: 0.999983 at lag 0        （未做任何对齐，天然同步）
t(s)   outRMS    voRMS   ratio
   0   0.15872   0.15882  0.9994
 120   0.14933   0.14943  0.9994
 240   0.15032   0.15042  0.9993
 360   0.14679   0.14688  0.9994
 480   0.15326   0.15336  0.9993
```

0.9994 的幅度比正是 AAC 有损编码该有的损耗；波形本身是同一段配音。

**旧目标保护仍然有效**：把配音指向一个不存在的文件、目标指向一个已有 MP4 → 退出码 1，
失败信息 `Failed to read voiceover file: …`，目标 SHA256 `2e614fe4…` 不变，0 残留。
（渲染跑了 40 秒之后才失败，说明保护点在提交那一步，不在读取那一步。）

### 6.2 内存到底花在哪（改之前 2085 MB 峰值）

`mixVoiceoverIntoVideo` 这条路上，一次 10 分钟混音在 renderer 里同时存在：

| 分配 | 10 分钟量级 | 说明 |
|---|---|---|
| `readVideo` 的 ArrayBuffer | 214 MB | 渲染 stage 整个读进渲染进程 |
| `new Blob([video])` 的 blob 存储 | 214 MB | 给 mediabunny 的 `BlobSource` |
| `videoBlob.arrayBuffer()` | 214 MB | **同一个文件的第二份 ArrayBuffer**，只为解码原音轨 |
| `decodeAudioData(data.slice(0))` | 214 MB | 又一份拷贝，因为 `decodeAudioData` 会 detach |
| 解码出的原音轨 AudioBuffer | 230 MB | 600 s × 48 k × 2 ch × f32 |
| 解码出的配音 AudioBuffer | 230 MB | 同上 |
| OfflineAudioContext 渲染目标 | 230 MB | 同上 |
| `BufferTarget` 的整段输出 | 201 MB | mediabunny 在内存里攒完整个 MP4 |
| `new Blob(buffer)` → `.arrayBuffer()` | 201 MB | 又一份 |
| IPC 到主进程的结构化克隆 | 201 MB | 主进程侧的副本 |

峰值 2085 MB 与这张表吻合。**其中三项是纯浪费**：第二份 ArrayBuffer、`slice(0)` 的拷贝、
以及输出在 Blob 与 ArrayBuffer 之间来回一趟。

### 6.3 最小修复（不是重写混音器）

只改 `src/lib/exporter/voiceoverMix.ts` 与它的唯一调用点，三处：

1. `mixVoiceoverIntoVideo` 接受 `Blob | ArrayBuffer`。调用方手里已经有 ArrayBuffer，
   不再"包成 Blob 再读回来"。
2. 原音轨解码改为**接管**调用方的 buffer（`decodeToBuffer(..., true)`），去掉 `slice(0)`：
   这份数据此后没人再读，复制它没有意义。
3. 返回 `BufferTarget.buffer` 本体（`ArrayBuffer`），不再 `new Blob()` 让调用方再 `arrayBuffer()`。

| | 改之前 | 改之后 | 差 |
|---|---|---|---|
| renderer peak WS | 2085.4 MB | **1830.3 MB** | **−255 MB（−12.2%）** |
| renderer max private | 1908.9 MB | 1652.7 MB | −256 MB |
| main peak WS | 822.8 MB | 824.1 MB | ±0 |
| gpu peak WS | 122.4 MB | 122.5 MB | ±0 |
| 耗时 | 128.2 s | 128.7 s | 噪声 |
| 输出大小 | 201,562,724 B | 201,562,724 B | **完全相同** |

**输出是否被改坏**：两个文件整体 SHA256 不同（`4c34cb2c…` vs `44262095…`），但
`cmp -l` 只有 **20 个字节**不同，全部是容器里的 creation/modification time（`ffprobe` 也印证
`creation_time` 变了）；**视频流 MD5 与音频流 MD5 两个文件完全相同**。
所以修复是内容中性的。

剩下 1830 MB 的大头是"整个音频在 OfflineAudioContext 里解码 + 整个 MP4 在内存里封装"，
那是这套设计本身；把它变成流式要重写混音器与 mux 目标，任务书明确要求"未经证明不要重写"，
本轮到此为止，列为下一轮的候选。

**一个必须说清楚的行为**（不是本轮引入的）：编辑器的"保存项目"写的是**它自己的工程副本**

所以"从任意路径打开一个工程、保存"之后，**原文件不变**（实测 `originalUntouched: true`），
改动落在应用管理的副本里，应用的项目列表里看到的就是那份。本轮按这个既有语义验收（重开的是副本），
没有改它——改它会触到整个文档存储的路径模型，属于另一件事。见 §11 的"潜在风险"。

## 11. 未完成事项

### 已确认缺陷（本轮新发现，未修）

无"导出失败"级缺陷。**一条确认的行为**：§7 末尾所述——"保存项目"写的是应用管理的副本，
不更新你打开的那个外部文件。这不是本轮引入的，也不是长视频特有的，但会让"打开外部工程 → 改 → 保存 → 重开原文件"
看起来像丢改动。列在这里，等下一轮决定是修行为还是修文案。

### 潜在风险

1. **混音内存仍是整文件量级**：10 分钟 1.83 GB，**30 分钟实测 4.6 GB（renderer 峰值 4665.6 MB）**。
   63 GB 机器上不构成阻塞（本轮 30 分钟混音完整跑完），但在 16 GB 机器上会明显吃紧、8 GB 机器上基本不可用。
   要根治得把音频渲染和 MP4 封装改成流式。
2. **`--quality` 的 bitrate 在本机 NVENC 上无效**（§3.2 的 `option refusée`），码率由 NVENC 默认质量决定。
3. **硬杀留下的残留只在"下次往同一目录导出"时清理**，不做启动扫描——这是任务书要求的方向，
   但意味着一个再也不导出的目录会一直留着那几个文件。
4. **stale stage 的 PID 不可知**：stage 名字不带 PID，只能靠 24 小时 + 本进程登记来保护；
   跨进程并发导出同一目录的极端情况下，靠"未过期"这一道闸门兜底。

### 环境阻塞

- **CPU HEVC @1598×1080 = BLOCKED**（V2.3.1 已证：libkvazaar 要求 8 的倍数，padded 路线已证伪）。
  本轮未重新触碰。
- Intel QSV：无硬件。

### 未实际运行

- macOS / Linux：只做了共享代码的静态检查（改动全在 Electron 主进程与渲染层的 TS，`Blob`/`ArrayBuffer`/
  `process.kill` 三处都是跨平台的）；**未编译、未运行**。
- Windows 播放器兼容性（系统播放器 / VLC / 剪辑软件打开导出的 H.265）：未做。
- 长视频 GUI 导出**中途关窗口/强杀**：只做了 Cancel 与 CLI SIGTERM（V2.4），本轮未重复。
- **30 分钟混音只走了 CLI**：GUI 的配音入口这次没有点过（§6.4 的两条混音都是 `--audio`）。

## 12. 最终结论

**V2.5 是否通过？** 通过。五个任务全部有真实运行证据：A 有编码器名/帧数/全片解码，B 有 143 ms 响应与
前后 SHA256，C 有先失败后通过的单测 + 真实导出清理，D 有音轨相关度 0.999983 与 OS 高水位内存，E 有字段级对照。

**长视频是否达到稳定使用要求？** 对 **H.264 / H.265 的 30 分钟导出**：是。V2.4 修掉的 MP4 校验缺陷、
V2.2 的设备选择、V2.3.1 的首帧回退，加上本轮的取消与残留清理，这条路径在本机已经连续跑通多次且字节可复现。
对 **30 分钟带配音混音**：**功能通过、资源不合格**——4.6 GB 的 renderer 峰值在本机（63 GB）没问题，
在 16 GB 机器上会吃紧。这是本轮唯一一条"能用但不够稳"的结论。

**是否需要下一轮修复？** 有两条值得排进去：
① 混音的流式音频/流式封装（把 1.8 GB 降到几百 MB）；
② §7 那条"保存写副本"的行为定义。
另外 §11 的 bitrate 无效属于参数调优，可一并看。

**是否建议进入实际使用观察？** 建议。本轮之后没有已知的"导出直接失败"缺陷；建议在真实项目上
连续观察一段时间，重点记录 30 分钟以上、带配音的导出是否出现内存告警。
