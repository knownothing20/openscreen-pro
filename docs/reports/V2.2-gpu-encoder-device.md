## 2. 显卡识别结果（本机实测）

`listGpus()` 返回 DXGI 的 6 个条目，归并后 3 类（见 §3 的重复说明）：

| # | 名称 | 厂商 | Vendor/Device | LUID | 显存 | 软件适配器 |
|---|---|---|---|---|---|---|
| 0 | AMD Radeon 780M Graphics | AMD | 1002:1900 | `0000000000013f81` | 512 MB | 否 |
| 1 | NVIDIA GeForce RTX 4070 Ti SUPER | NVIDIA | 10DE:2705 | `000000000438724d` | 16063 MB | 否 |
| 2 | NVIDIA GeForce RTX 4070 Ti SUPER | NVIDIA | 10DE:2705 | `00000000000209c0` | 16063 MB | 否（重复条目） |
| 3 | AMD Radeon 780M Graphics | AMD | 1002:1900 | `000000017516a0ec` | 512 MB | 否（重复条目） |
| 4/5 | Microsoft Basic Render Driver | Microsoft | 1414:008C | …5c10 / …5c61 | 0 | **是**（WARP） |

**重复条目是真实存在的**：同一块物理卡被 DXGI 列出两次（不同 LUID）。UI 按 `vendorId:deviceId:name` 归并成一项并标注"2 driver entries"；设置里存的是**第一项的 LUID**。

## 5. 设置保存与重启

- 在对话框里点选 NVIDIA → 设置文件 `recording-settings.json` 立刻出现 `"lastEncoder": {"device": "000000000438724d"}`（由 Playwright 读取文件确认，走的是 UI→IPC→store 的真实路径）。
- **跨进程验证**：之后的每一次 CLI 导出都是新进程，均按该 LUID 使用 nvenc（§7），说明选择在重启后仍然生效。
- 切工程不影响：CLI/GUI 都从应用级设置读，不读工程文件。
- 旧安装兼容：没有该字段（或值非法）时读作 `auto`。

## 6. GUI 与 CLI 是否同一机制

是。两者都调 `window.electronAPI.getEncoderPrefs()` → 同一个 store → 同一个 `encoderDevice` 字段 →
同一个 `compositor.exportMulti` → 同一个 `create_export_gpu`。CLI 侧代码注释写明了理由：两边分叉正是那种"应用里很快、命令行很慢"的工单来源。

## 8. CPU fallback（真实测试）

`device=cpu` → 编码器 **libopenh264**、路径 **系统内存**、文件明显更小（450 KB vs 974 KB）。
**修复记录**：第一版把 `h264_mf` 也算作"软件"，实测该档跑出 1,125,110 B / 3324 ms——MediaFoundation 会
解析到硬件 MFT，这与"CPU 软件编码"的承诺不符。改为只接受自带实现的 `lib*` 编码器后复测为 libopenh264。

## 9. 实际编码器与 GPU 身份证明

原生侧每次导出都打印（不是配置值，是 `avcodec_open2` 真正打开的那个）：
`[pipeline] encodeur vidéo : h264_nvenc (textures D3D11, zéro-copie)`。
adapter 名字读自**已创建设备**的 DXGI descriptor（`GetAdapter()->GetDesc1()`），不是请求值；
Playwright 的测试编码结果行（§4）就是这条链路的下游产物。

## 10. 性能对比（42.566 s / 2554 帧，同一工程同一参数）

| 设置 | 编码器 | 路径 | 导出耗时 | 文件 |
|---|---|---|---|---|
| auto | h264_amf | 零拷贝 | 12,015 ms | 77,748,544 B |
| NVIDIA | h264_nvenc | 零拷贝 | **11,260 ms** | 36,200,378 B |
| AMD | h264_amf | 零拷贝 | 12,131 ms | 77,748,544 B |
| CPU | libopenh264 | 系统内存 | **24,902 ms** | 16,893,044 B |

**诚实解读**：202.5 帧/s vs 210.9 帧/s — NVENC 只快 6%，因为这条管线是**合成/解码受限**，不是编码受限；
真正说明问题的是 CPU 档 2.1× 慢。另外同等码率目标下 NVENC 输出只有 AMF 的一半，说明两个驱动对
rate control 的解释不同（不是本轮引入的问题，但也意味着"换卡后文件大小会变"）。
未采集 GPU 引擎占用率：本机没有可靠的自动化计数器，任务管理器读数不足以作为证据，故不写。

## 11. D3D11 零拷贝是否保留

保留。三条硬件路径（auto/AMF、NVIDIA/NVENC、AMD/AMF）全部打印 `textures D3D11, zéro-copie`——
因为"选择设备"实现为**在目标卡上建设备**，合成、解码、编码仍共用一个 `ID3D11Device`，
不存在跨卡拷贝。若所选卡没有厂商编码器，则**明确失败**而不是悄悄换卡（`Manual` 语义）。
