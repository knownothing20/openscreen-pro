## 5. 子进程生命周期与取消（PASS，含 1 处 P1 修复）

### 5.1 取消链路

`AbortController → SIGTERM → (3 s 未退出) SIGKILL → close → 清理 partial → 抛 VoiceoverMixCancelled`，
`close` 之后才删文件（Windows 上写入中的句柄锁着文件，`discardExportFile` 有 EBUSY/EPERM 重试）。

实测（30 分钟 render + 1800 s 配音，服务层真实子进程）：

| 项 | 结果 |
|---|---|
| 取消响应 | 触发后 **152 ms** 收敛（总 1158 ms，含 1 s 延迟触发） |
| 输出文件 | 无 stage、无 partial |
| 残留 ffmpeg | 0 |
| 取消后立即重跑 | 28.4 s 成功，588,557,904 B，`hvc1` 108,000 帧 |
| 双重提交 | 不可能：commit 在事务最后一步，混音失败直接抛出；取消与完成竞争只收敛到一个结果 |

### 5.2 主进程被硬杀时的 FFmpeg（重点）

用 Electron 宿主直接调用生产函数（545 MB render + 1800 s 配音），混音进行中用 `TerminateProcess`
**只杀主进程 pid**（等同任务管理器"结束任务"）：

```
before: main=45084 ffmpeg=1 partial=48,234,540 B
kill main
t+1.5s ffmpeg=0 partial=48,496,684 B   ← 子进程已退出，文件停在最后一次 flush
t+12s  ffmpeg=0 partial=48,496,684 B   ← 不再增长
```

结论与边界：

- **没有出现"主进程死了、ffmpeg 继续写"**：子进程在 1.5 s 内退出（其 stderr 管道随父进程关闭）。
  同一现象在纯 Node 宿主上重复过一次（48,234,540 → 74,186,796 B 后终止）。
- **实现上没有 Job Object**，所以这是**实测行为，不是强制保证**。若将来 ffmpeg 卡在不出日志的状态，
  理论上可能多活一会儿；记录为 P3 建议（Windows Job Object 需原生代码，本轮不做）。
- **partial 里的 PID 是"发起混音的主进程"**（`process.pid`），不是写文件的 ffmpeg。这是有意的：
  混音结束后由主进程 rename；崩溃时主进程已死，该文件因此**可归属**给本应用并被清理器接受。
- **清理器不会把仍在写入的文件当孤儿**：两道闸门——① 登记中的活跃路径不删；② 24 h 过期。
  一个混音最多几十秒，远小于 24 h，所以"活着在写但名字里的 PID 已死"这个窗口与删除条件不可能同时成立。
- 实测印证：被杀后留下的 48 MB 截断 partial 在**新鲜时**经历一次真实导出未被删除（§7）。

## 12. 新发现问题及修复

### 12.1 P1（已修）：已被取消的信号会被忽略，混音照常完成并写盘

**触发条件**：调用方在进入 `mixVoiceoverToFile` 之前（或两次 probe 之间）就已 `abort()`。
`AbortSignal.addEventListener` 不是追溯性的，监听器注册时事件早已发生过，于是永远不会触发；
子进程随后启动、跑完、写文件，返回成功。

**复现（修复前的实测）**：

```
const c = new AbortController(); c.abort();
await mixVoiceoverToFile(request, { signal: c.signal })
→ RESOLVED despite an aborted signal in 394 ms
→ preabort-out.mp4 970,889 B 已写出
```

产品含义：用户点了取消、事务却拿到成功并 **commit**——正是任务书点名禁止的"先报取消，随后又提交"。

**修复（2 行判断，无行为变化）**：

- `mixVoiceoverToFile` 入口：`if (options.signal?.aborted) throw new VoiceoverMixCancelled()`（不 spawn、不读盘）；
- `runChild` 注册监听器后：`if (options.signal?.aborted) onAbort()`（覆盖"注册前一刻被取消"的窗口）。

**测试**：新增 2 条——"预先取消的信号必须被拒绝且不落盘"（<100 ms 返回、无文件、无 partial）、
"在 probe 阶段取消"（`abort()` 在 0 ms 触发 → `VoiceoverMixCancelled`、无文件）。
修复后 27/27 通过；修复前后对照即上面的 394 ms / 970,889 B。

### 12.2 P2（观察，不改代码）：没有 Job Object，子进程随父进程退出靠的是管道

见 §5.2：实测主进程被 `TerminateProcess` 后 ffmpeg 在 1.5 s 内退出、文件停止增长。
这不是强制保证（没有 Job Object），但清理器的两道闸门（活跃登记 + 24 h）不依赖它。
本轮不改；若将来要做强制保证，需要 Windows Job Object（原生代码），属于新工作量。

### 12.3 P3（记录，不改）

1. **`dist-electron/` 会累积历史 bundle**：每次 `vite build` 新增一个 `main-<hash>.js` 而不清理旧文件，
   打包会把它们全部塞进 asar（本次清出 4.3 MB）。建议在 before-pack 里删掉未被 `main.js` 引用的 bundle。
2. **`jobId` 用毫秒时间戳**（`cli-mix-${Date.now()}`）：同进程同毫秒两次混音会撞 id，取消会错杀。
   产品里一次 CLI 导出只跑一个混音，无法复现；改用 `randomUUID()` 更稳。
3. **`renderPath` 不要求是 stage 名**：IPC 只强制 `outPath` 必须是本应用的 stage（写权限），
   `renderPath` 是只读输入，接受任意绝对路径。不构成越权（renderer 本就能读文件），记录备查。
