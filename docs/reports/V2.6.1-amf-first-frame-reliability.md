# OpenScreen V2.6.1 — AMD AMF 首帧可靠性收尾

**结论：COMPLETE。**

## 3. AMF 真实失败根因

### 3.1 证据链

V2.6 观察的 6 份失败日志，**每一份都恰好包含一条** DXGI 报错，成功日志里一条都没有：

```
[pipeline] encodeur vidéo : h264_amf (textures D3D11, zéro-copie)          ← 编码器已选定（probe 已通过）
[compositor] wallpaper image "…wallpaper4.jpg" : GPU 设备实例已经暂停。
             使用 GetDeviceRemovedReason 以确定相应的措施。 (0x887A0005)   ← 设备被移除
native bridge compositor.exportMulti failed: Error: send_frame: -1313558101 (Unknown error occurred)
```

- `0x887A0005` = `DXGI_ERROR_DEVICE_REMOVED`。
- `-1313558101` 是 `av_strerror` 认不出的码，所以显示 "Unknown error"，把真正的信号藏住了。
- 顺序证明：**probe 用的是一个新实例，它通过了**；随后正式实例的第一帧被拒。所以不是"AMF 会话建不起来"，而是**设备在 probe 之后、正式首帧之前进入了 removed 状态**。
- 修复后同一路径上真实抓到 2 次同类事件，`GetDeviceRemovedReason` 报的是 `0x887A0007` = `DXGI_ERROR_DEVICE_RESET`。两者同属"设备不可用"，`GetDeviceRemovedReason` 都会返回非 0。

### 3.2 因此被否定/保留的假设

| 假设 | 判定 |
|---|---|
| 双实例（probe + 正式）会话建不起来 | **否定**：probe 通过在先，失败在正式首帧 |
| 宽度/对齐限制 | 否定（V2.6 已在 1494/1598/1752/1920 四个宽度上复现过，与宽度无关） |
| 累积资源泄漏 | 否定（V2.6 的 8 连发、本轮 30 连发全过） |
| 驱动层设备复位（TDR/适配器丢失） | **成立**：DXGI 直接报出 removed/reset |

## 4. 首帧探测与正式编码的生命周期（审计结果）

```
create_export_gpu(device request)      → D3D11 设备 + 适配器（一次/导出）
Compositor::new_sized                  → 与导出尺寸一致的合成器
set_scene / set_live_params            → 壁纸等纹理上传（第一次真正用设备）
pipeline::run_composited_multi
  ├ VideoEncoder::open_with_probe      → 每个候选：开实例 → 送 1 帧 → receive_packet → drop 实例
  │                                      （probe 失败 = 该候选不可用，换下一个；不重试）
  ├ try_open 正式实例                   → 同一设备、同一参数再开一次
  ├ walk_composited_timeline           → 第 0 帧 send（本轮的失败点）
  └ flush / audio / trailer / teardown
```

审计发现的两处缺陷（都属于"错误路径"）：

1. **muxer 在错误路径上没有关闭**。只有取消分支显式 `avio_closep` + `avformat_free_context`；其它错误（包括首帧失败）直接 `?` 返回，`AVIOContext` 保持打开，Windows 上文件一直被锁。实测后果：重建后的第二次尝试能编码完，但最终 `rename` 报 `EBUSY: resource busy or locked`。
2. **取消分支与新增的统一清理会重复释放 `octx`**。这是我第一版补丁引入的（见 §5.3），被 GUI 取消测试抓出来。

## 5. 修改文件与代码位置

### 5.1 `crates/compositor/src/d3d_windows.rs`（+17）

新增 `Gpu::device_removed_reason() -> Option<u32>`，直接问 DXGI，而不是从 `av_strerror` 的 "Unknown error" 猜。

### 5.2 `crates/compositor/src/pipeline_windows.rs`（+203/−?）

- 帧循环：第 0 帧的 send 失败被标成 `first_frame: …`，与中途失败区分（中途失败**不允许**重试，否则要重写已编码的帧）。
- `is_first_frame_failure(msg)`：只认这个标记；**故意不匹配 probe 的 "first frame failed (…)"** —— 那是"候选不可用"，属于候选循环的事。
- `retry_allows_device_restart(choice)`：`Vendor(0x1002)`（手动 AMD）与 `Auto` 为真；`Vendor(0x10DE)`、`Vendor(0x8086)`、`Cpu` 为假。手动 NVIDIA/CPU 行为完全不变。
- **所有**错误路径统一收尾：关闭 muxer、释放 packet/format context、unref frames/hwdev，然后返回原错误。
- 取消分支不再自己关 muxer（交给上面的统一收尾），消除双重释放。
- 测试钩子（`encoder-test-hooks`，默认关闭、出货二进制中不存在）：
  - `injected_export_first_frame_failure()`：`OPENSCREEN_TEST_FAIL_EXPORT_FIRST_FRAME=1|always`，只作用于**正式首帧**，不作用于 probe；
  - `injected_device_removed()`：`OPENSCREEN_TEST_DEVICE_REMOVED=1`，让**同一个决策函数**回答"设备已移除"。
- 3 条新单元测试：首帧标记的精确性、只有 AMD/Auto 可重建、钩子在无 feature 时恒为 false。

### 5.3 `crates/compositor-view-napi/src/lib.rs`（+111/−?）

`compute()` 里把"建设备 + 建合成器 + 跑管线"包进**最多两次**的循环：

```
attempt = 1: 建设备/合成器 → 跑
  ├ 成功 → 返回
  └ 失败 → 记 reset choice → 取消? 返回 EXPORT_CANCELLED
        → retryable = attempt==1 && 是首帧失败 && 选择允许 && (设备报 removed 或注入)
        → 是：打日志，continue（同一 adapter、同一 codec、同一参数、同一目标路径）
        → 否：返回原错误
attempt = 2: 再失败 → 直接返回原错误（不会第三次）
```

日志（法语与现有 pipeline 日志一致，便于 grep）：

```
[pipeline] première frame refusée sur AMD Radeon 780M Graphics (0x887A0007), appareil D3D11 recréé — nouvelle tentative 2/2, même encodeur, même format
```

边界：只重建设备，不换 GPU、不换编码器、不降格式、不改分辨率/帧率/码控；输出文件由 `run_composited_multi` 自己丢弃重写，帧号从 0 起，**不会重复写入任何帧**。

## 10. Auto 的候选选择与回退证据

- 正常情况：Auto 输出 9,156,130 B，与手动 AMD **逐字节相同** ⇒ 本机 Auto 解析到 AMF（与 V2.2/V2.3 一致），不是 NVENC。
