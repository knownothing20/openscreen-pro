## 1. 开发结果：哪些是原本就有的

审计先于实现。**Rust 侧其实早就有 H.265**：`ExportCodec::H265`、候选链
`hevc_amf → hevc_nvenc → hevc_qsv → hevc_mf → libkvazaar`、napi 的 `"h265"` 解析，都是 V2.1
就存在的代码。缺的不是编码器，是**没有任何东西能选中它**：

| 位置 | 状态 |
|---|---|
| `exportMulti` 的 `codec` 参数 | 已支持 `h264`/`h265` |
| GUI 导出（`ExportDialog.tsx`） | **硬编码 `codec: "h264"`** |
| CLI 导出（`CliExportRunner.tsx`） | **硬编码 `codec: "h264"`**，且无 `--codec` 参数 |
| 设置 | 只有 `lastEncoder.device`，**没有格式字段** |
| `listGpus` 的 `encoders` | **两个格式混在一个数组里**，界面无法区分 |
| MP4 sample entry | HEVC 走 muxer 默认 → **`hev1`**（实测） |
| `libkvazaar` 的码控 | 设 `rc_mode`/`bitrate`，**这两个 AVOption 对它根本不存在** |

本轮补齐的就是这条链路，并修掉上面三个暗坑。

**新增（按层）**

- **设置**：`lastEncoder.codec`（`h264` | `hevc`，默认 `h264`）。V2.2.1 的
  `recording-settings.json` 里没有这个字段，读到就是 `h264` —— 升级后输出与升级前完全一致。
- **CLI**：`--codec h264|hevc`（`h265` 作为别名接受）。不传则读应用级设置。GIF 上给
  `--codec` 直接报错，而不是静默忽略。
- **napi**：新增 `codecSupport()`（本 build 每个格式有哪些编码器、有没有软件编码器）；
  `GpuInfo` 拆出 `encodersH264` / `encodersHevc`，`encoders` 保留为并集。
- **Rust**：`encoder_names_for(vendor, codec)` 按格式分组；`apply_rate_control` 给
  `libkvazaar` 改用 `kvazaar-params="rc-mode=cbr,bitrate=…"`；HEVC 输出显式写 **`hvc1`**；
  CPU 模式失败文案不再说 "GPU"；兜底失败文案从法语改成英语。
- **界面**：格式选择（H.264 / H.265，各带一句取舍说明）；每张卡**分两行**列出 H.264 与 H.265
  编码器；Test Encoder 按当前格式测；禁用原因改为 i18n key（此前是硬编码英文，中文界面里
  混着 "Software adapter — …"）。
- **修掉一个 V2.2.1 遗留缺陷**：Test Encoder 把存储值 `id:<PnP>` 直接交给原生层，而原生只认
  LUID —— 选真卡点测试必然报 `invalid encoder device`，而用同一张卡导出却正常。现在它走与
  导出相同的 `resolveEncoderDevice`。

## 4. H.264 与 H.265 对比（42.566 s / 2554 帧，good 档）

参考片：`--quality source` 输出降采样到 1598×1080 后 x264 CRF10。

| 编码器 | 文件大小 | 平均码率 | SSIM | PSNR | 导出耗时 |
|---|---:|---:|---:|---:|---:|
| H.264 NVENC | 36,200,378 | 6.79 Mbit/s | 0.987259 | 34.403 dB | 12,130 ms |
| **H.265 NVENC** | **30,666,536** | 5.75 Mbit/s | **0.987290** | **34.414 dB** | **11,954 ms** |
| H.264 AMF | 77,748,544 | 14.61 Mbit/s | 0.987165 | 34.389 dB | 14,346 ms |
| **H.265 AMF** | **78,533,878** | 14.76 Mbit/s | 0.987251 | 34.384 dB | 14,362 ms |

**要回答的问题，逐个来：**

- **H.265 比 H.264 省多少？** 取决于编码器，不取决于格式标签。NVENC 上省 **15.3 %**
  （36.2 → 30.7 MB），且 SSIM 还高了 0.00003。AMF 上**反而大 1.0 %**。
- **相同视觉质量下谁更省体积？** 在 NVENC 上是 HEVC（同 SSIM 0.9873，码率低 15 %）；在 AMF
  上是平手（同 SSIM，码率也几乎相同）。**没有出现"H.265 省一半"** —— 两个编码器都基本命中
  同一个码率预算，HEVC 的效率优势在 NVENC 上有，在 AMF 的这次实现里没有体现。
- **哪块 GPU 更快？** NVENC（约 12.0 s）比 AMF（约 14.4 s）快 17 %；同卡内 H.264 与 H.265
  耗时差异在 ±1 % 内，看不出区别。
- **CPU HEVC 值得提供吗？** 见 §7：`libkvazaar` 在 1598×1080 打不开，实际不可用于本项目
  的默认分辨率。
- **质量档位需要为 HEVC 单独调整吗？** 不需要。4 条路径的 SSIM 落在 0.98716–0.98729、
  PSNR 落在 34.38–34.41 dB，差别在噪声级别。为了"数字一致"去改档位只会牺牲画质。

## 5. 真实 MP4 验收

| 文件 | 容器 tag | 完整解码 `ffmpeg -v error -i … -f null -` | 音轨 | 时长 |
|---|---|---|---|---|
| nv-h264 | h264 / avc1 | 无输出（通过） | aac 48000 2ch | 42.566 s |
| nv-hevc | **hevc / hvc1** | 无输出（通过） | aac 48000 2ch | 42.566 s |
| amd-h264 | h264 / avc1 | 无输出（通过） | aac 48000 2ch | 42.566 s |
| amd-hevc | **hevc / hvc1** | 无输出（通过） | aac 48000 2ch | 42.566 s |

- **`hvc1` 是显式设的**。FFmpeg 的 mov muxer 对 HEVC 默认写 `hev1`（实测 `(hev1 / 0x31766568)`），
  而 `hvc1` 要求参数集只在 `hvcC` 里 —— 编译器一直通过 `extradata` 提供 SPS/PPS，所以两者都合法，
  但 `hvc1` 是 Apple 的解复用器和部分 Windows 播放器认的那个。
- **HEVC + 配音**：混音是 remux（`EncodedVideoPacketSource` 直拷视频包，不重编码），实测输出仍是
  `hevc / hvc1` + `aac 48000 2ch`，完整解码无错误，0 个 stage 残留。**没有降级成 H.264。**
- **OpenScreen 自己能读**：在打包版里用真实的 `<video>` 元素加载导出的文件，
  `nv-h264` → 1598×1080 / 42.57 s / 无错误，`nv-hevc` → **1598×1080 / 42.57 s / 无错误**。
- **播放器兼容性是另一件事**：本轮只证明"文件结构正确、FFmpeg 与 Chromium 都能完整解码"。
  没有在 VLC / 播放器 / 资源管理器缩略图里逐个试，也没验证 Windows 是否装了 HEVC 视频扩展。
  **编码成功 ≠ 每台 Windows 都能播**，这一条明确记为 NOT_RUN。

## 附：这一轮最重要的一句话

H.265 的价值不是"文件一定更小"，而是"同样的画质可以用更少的码率"——这需要在**每个编码器
自己身上**测量才能断言。本机的结果是：NVENC 兑现了 15 %，AMF 没有兑现。把它写成
"启用了 H.265 所以省一半"，就是拿格式名当结论。
