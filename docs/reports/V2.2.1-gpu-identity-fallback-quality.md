## 1. GPU 设备身份

### 旧方案的问题（V2.2）

存的是 DXGI LUID。LUID 是**运行时句柄**：驱动更新、会话切换、设备重新枚举都可能变；
更直接的证据是 V2.2 自己的枚举结果——同一块卡被 DXGI 列了两次，两个**不同的 LUID**。用它当永久身份，
等于把"这次开机时它是谁"当成"它永远是谁"。

### 稳定身份用的是什么

`stable_id` = **PnP 设备实例 ID**，例如
`PCI\VEN_10DE&DEV_2705&SUBSYS_413C1458&REV_A1\4&25C6DA53&0&0009`。

获取方式：`SetupDiGetClassDevs(GUID_DEVCLASS_DISPLAY)` + `SetupDiGetDeviceInstanceId`，
再用 DXGI `AdapterDesc1` 的 `VendorId/DeviceId/SubSysId/Revision` 拼出 `VEN_..&DEV_..&SUBSYS_..&REV_..`
去匹配设备树里的实例 ID。

**这里踩了一个坑，值得记下来**：最直觉的 `EnumDisplayDevicesW` 在本机（RDP 会话）只返回
**16 个一模一样的 `RDPIDD_INDIRECTDISPLAY`**（远程间接显示驱动），一块物理卡都没有。
如果按它的结果做匹配，所有 GPU 都会退化成"身份待确认"。改成走设备树（SetupAPI）后，两块卡立刻正确配对。

### 重复设备怎么判断

- 两条 DXGI 条目 → **同一个**稳定 ID（同一块卡被驱动列了两次）→ 归并成一项，标注 "2 driver entries"。
- 两张**同型号**的卡 → PCI 片段相同、实例 ID 不同 → 匹配到多个 → 标记 `identity_ambiguous`，
  **不归并**，并且用户若选中它，导出会明确报"匹配到多于一块卡，无法固定"而不是随便选一张。
- 完全没有 PCI 身份的适配器（WARP / 虚拟显示）→ `pci:VEN_..` 兜底 + `identity_ambiguous=true`。

### 重启后如何映射

设置里存 `id:<stable_id>`；每次导出前用当前 DXGI 列表把 `id:` 解析成本次会话的 LUID。
实测（两次独立启动应用）：`recording-settings.json` 保持
`id:PCI\VEN_10DE&DEV_2705&SUBSYS_413C1458&REV_A1\4&25C6DA53&0&0009`，两次启动的对话框都选中
NVIDIA 那张卡并显示该设备 ID（截图 `b21-v21/v221ui/01-restored.png` / `02-after-restart.png`）。

### 旧 LUID 兼容

V2.2 存的裸 LUID 仍然可读：第一次成功解析后就地改写成 `id:<stable_id>`。
实测：把设置写成 `000000000438724d` → 导出成功 → 文件变成
`"device": "id:PCI\\VEN_10DE&DEV_2705&SUBSYS_413C1458&REV_A1\\4&25C6DA53&0&0009"`（保留大小写）。
解析失败（设备已不在）时**不是**回退 auto，而是导出失败并说明是哪张卡。

> 期间修复的一个真实缺陷：`parseEncoder` 最初没有 `id:` 分支、且写入时对整体 `toLowerCase()`，
> 结果是"存了 stable id 但读出来是 auto，导出悄悄用了核显"。已修 + 3 条回归测试钉住（大小写保留、LUID 归一化、乱码读作 auto）。

## 2. 自动回退（真机 + 故障注入）

故障注入手段：环境变量 `OPENSCREEN_TEST_FAIL_ENCODER=h264_nvenc`，在候选规划阶段把这些编码器
当作"打开失败"剔除——这样在真机上就能演练"驱动拒绝"这条控制流，而不必去破坏驱动。

| 场景 | 期望 | 实测 |
|---|---|---|
| Manual NVIDIA（正常） | h264_nvenc | **h264_nvenc**，零拷贝 |
| Manual AMD（正常） | h264_amf | **h264_amf**，零拷贝 |
| CPU | 只接受 `lib*` | **libopenh264**，系统内存 |
| **Manual NVIDIA + nvenc 注入失败** | **失败，不许换卡** | **失败**：`the selected GPU's encoder could not be opened: h264_nvenc: injected failure` |
| **Auto + nvenc 注入失败** | 回退到下一个 | **h264_amf**，成功 |
| **CPU + libopenh264 注入失败** | 失败 | **失败**：同一条格式的原因 |

线程安全：选择与报告都是 **thread-local**，一次导出从头到尾在同一条 worker 线程上；
3 条 Rust 测试分别验证"报告只被消费一次""取走后选择复位""另一条线程看不到本线程的选择"。

## 3. 编码质量

### 审计结论（先查原因，不改参数）

`ctx.bit_rate` 一个字段对三种编码器含义不同：
- NVENC 默认 VBR，按目标**预算**走，静态画面内容下明显低于预算；
- AMF 默认 `cqp`（恒定 QP），根本没有码率概念 —— V2.2 里 77.7 MB 的来源；
- openh264 默认质量模式，同样忽略预算（实测 28.6 MB）。

本轮改成**按各自语义声明码控方式**（不改 preset、不改档位）：
`h264_nvenc rc=1(vbr) + bitrate`、`h264_amf rc=2(vbr_peak)`（AMF 没有 `bitrate` AVOption，
实测 `option bitrate=… refusée (ret=-1414549496)`，它读的是 `ctx.bit_rate`）、
`libopenh264 rc_mode=2 + bitrate`。

中途有一次反复值得记录：第一版还设了 `maxrate == bitrate`，把 NVENC 从 6.8 Mbit/s 压到 5.5 而画质无提升，
已去掉——**预算是预算，不是下限**。

### 客观测量（同一工程 42.566 s / 2554 帧 / 1598×1080 / 60fps / `--quality good`）

参考片：同一时间线的 `--quality source` 输出（2880×1946 / 15.1 Mbit/s）用 lanczos 降到 1598×1080，
x264 CRF 10 编码（20.9 MB），作为无偏参考。

| 编码器 | 文件 | 平均码率 | SSIM | PSNR | 导出耗时 |
|---|---:|---:|---:|---:|---:|
| h264_nvenc | 36,200,378 B | 6.79 Mbit/s | **0.987259** | **34.403 dB** | 12,039 ms |
| h264_amf | 77,748,544 B | 14.61 Mbit/s | **0.987165** | **34.389 dB** | 13,081 ms |
| libopenh264 | 28,616,390 B | 5.37 Mbit/s | **0.986130** | **34.383 dB** | 26,067 ms |
| （参考） | 20,943,648 B | — | 1.0 | ∞ | — |

**结论：三者视觉质量在测量误差内相同（SSIM 差 0.0011、PSNR 差 0.02 dB），体积差 2.1 倍是编码器效率差异，不是质量差异。**
所以"统一质量档位"的正确做法不是把三者拉到同一码率——那会让 NVENC 的文件凭空翻倍而画质不变。
档位语义保持原样（预算），码控方式已显式化，文件大小差异作为已知特性记录。
没有为了数字一致去降低任何一档的画质。

## 5. 持久化

- 选择：`id:<stable_id>`，重启后恢复（两次启动实测，见 §1）。
- 模式：`auto` / `cpu` / `id:` 三种值，均在同一个字段里，旧文件兼容。
- 设备不可用：设置里保留原值（对话框仍显示"不在本机"，导出拒绝），不会静默改用别的卡。

## 9. 未完成 / 已知限制

1. **驱动版本**：Rust 侧已从显示类键读取 `DriverVersion`，但本机返回空（`SPDRP_DRIVER → 类键` 读取无值），
   界面**不显示**该字段。标 **NOT_AVAILABLE**，不是"未实现"，是这台机器取不到。
2. **Intel QSV**：本机无 Intel GPU → **NOT_RUN**（候选规划已有测试覆盖 `Vendor(0x8086) → h264_qsv`）。
3. **H.265 实机导出**：GUI/CLI 仍固定 h264，设备过滤对 hevc 同样生效但未跑真机 → **NOT_RUN**。
4. **VMAF**：系统 ffmpeg 带 libvmaf 滤镜，但无模型文件；按"不重复下载工具"的要求改用 SSIM/PSNR → **PARTIAL**。
5. **`debug_pnp_adapters`**：一个只读诊断入口（返回设备树原始列表），保留用于支持排查"为什么我的卡没出现"。
6. **同型号双卡**：会正确标记 `identity_ambiguous` 并拒绝固定，但本机没有两台同型号卡可实测 → 逻辑由单测覆盖。
