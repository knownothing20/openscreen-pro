## 1. 两个问题的最终结果

**HEVC 首帧失败能否正确回退？—— 能，且已用真实硬件证明。**

V2.3 把 `avcodec_open2` 成功当作"编码器可用"。`hevc_mf` 是反例：它打开成功，然后第一帧
`send_frame` 返回 `-542398533 (Generic error)`，整次导出就此中断，后面还排着 `libkvazaar`。

修法是**在候选选择阶段加一次真实首帧探测**：每个候选先在一个**用完即弃**的编码器实例上，
用它将来要吃的同一帧（compositor 的 NV12 / 合成用的 D3D11 纹理，与导出同尺寸同像素格式）
走一遍 `send` + `receive_packet`；失败就记一笔、丢弃、试下一个；通过才重新打开一个干净实例
用于正式编码。

两处刻意的设计：

- **丢弃探测实例，重新 open**。复用被探测过的实例会让 GOP 状态带上那一帧、时间线整体偏移。
  代价是每个成功候选多一次 open（约 100 ms），对比 12 秒的导出可以忽略。
- **探测帧是真实的一帧**，不是凭空构造的图。`send` 走的是导出同一条路（零拷贝 / 系统内存
  两条分支都在内），所以"探测通过"和"导出能出画面"是同一件事。

`receive_packet` 返回 `EAGAIN` 不算失败——那是编码器有前视延迟（`libkvazaar` 的 `--owf`），
不是它坏了。

**CPU HEVC 支持 1598×1080 吗？—— 不支持，而且这次是证明出来的，不是猜的。**

先做了实验，再下结论（`pipeline_windows::hevc_software_geometry`，两个常驻测试）：

| 尝试 | 结果 |
|---|---|
| `libkvazaar` 直接开 1598×1080 | 拒绝：`Video dimensions are not a multiple of 8` |
| 声明 `width=1598` 但 `coded_width=1600`（"编码 1600、声明 1598"）| **open 竟然成功** —— 因为它的封装校验读的是 coded 尺寸 |
| 按上面这条路真编 12 帧、写 MP4、再读回来 | 文件是 **1600×1080** |

最后一条是决定性的：`libkvazaar` 把**编码尺寸**写进码流和容器，**不写 conformance window**。
所谓"补 2 列再裁掉"根本不存在——多出来的 2 列会成为画面的一部分，1598 的导出变成 1600 宽。
所以没有实现它，而是把这条路的失败钉成了测试：将来 FFmpeg 若开始写 conformance window，该测试
会失败并提示可以重新考虑。

**界面能否准确识别？—— 能，这是本轮实际解决 CPU HEVC 可用性的方式。**

设置界面现在按**当前工程真实的导出尺寸**判断：

- 1598×1080 + H.265 + CPU → CPU 行**禁用**，并写明
  `软件编码要求宽高都是 8 的倍数 —— 本次导出为 1598×1080。`
- 同一个尺寸 + H.264 → CPU 行**可用**（`libopenh264` 没有这个约束）。
- 1280×720 的工程 + H.265 + CPU → 可用。

限制从"导出时才发现"提前到了"选择时就说明"。

## 3. Auto 回退的真实日志（hooks 构建，注入"首帧失败"）

**成功回退（本轮的核心证据）**——`Auto + H.264`，注入 `h264_amf` 首帧失败：

```
auto-h264-amf-ff-fail   ok=true   enc=h264_mf   1,125,110 B
écartés : h264_amf: first frame failed (injected first-frame failure for h264_amf)
          ; h264_nvenc: avcodec_open2(enc): -2 (No such file or directory)
          ; h264_qsv: avcodec_open2(enc): -1313558101 (Unknown error occurred)
```

候选 1 首帧失败 → 候选 2、3 真开不起来 → 候选 4 `h264_mf` 成功。**V2.3 时这里会直接中止。**

**HEVC 全链走到底**——`Auto + H.265`，注入 `hevc_amf` 首帧失败：

```
hevc_amf: first frame failed (injected first-frame failure for hevc_amf)
hevc_nvenc: avcodec_open2(enc): -2 (No such file or directory)        ← Auto 的默认设备是 AMD
hevc_qsv:  avcodec_open2(enc): -1313558101 (Unknown error occurred)
hevc_mf:   first frame failed (send_frame: -542398533 (Generic error)) ← 真实的 mf 首帧失败
libkvazaar: avcodec_open2(enc): -40 (Function not implemented)         ← 1598 不是 8 的倍数
→ ok=false, 0 字节, 未降级 H.264
```

第 4 行是重点：**`hevc_mf` 的真实首帧失败现在被探测抓住了**，不再被当成可用候选。

**Manual 与 CPU**（都必须明确失败，不换卡、不换格式）：

| 场景 | 结果 |
|---|---|
| Manual NVIDIA + `hevc_nvenc` 首帧失败 | `the selected GPU's encoder could not be opened: hevc_nvenc: first frame failed…` |
| Manual AMD + `hevc_amf` 首帧失败 | 同上（AMF） |
| Manual NVIDIA + `h264_nvenc` 首帧失败 | 同上（H.264 同样适用） |
| CPU + `libkvazaar` 首帧失败 | `no software encoder could be opened: libkvazaar: …` |
| 同构建不注入（对照 ×3） | `hevc_nvenc` / `hevc_amf` / `h264_amf`，全部成功 |

## 4. Test Encoder 与正式导出是否同参数

**现在同尺寸、同码率、同帧率、同像素格式、同码控。** 之前硬编码 1280×720，是"测试通过、
导出失败"的根源。

做法是把导出对话框的尺寸计算抽成 `resolveExportGeometry()`（`src/lib/exporter/exportGeometry.ts`），
两个对话框共用同一份逻辑；测试编码用它的 `width/height`，fps 用导出默认的 60，码率由同一函数
按尺寸和帧率算出。测试帧数仍缩短为 1 秒，编码条件不变。

实测（打包版，工程导出尺寸 1598×1080）：

```
CPU + H.265    → 行禁用：软件编码要求宽高都是 8 的倍数 —— 本次导出为 1598×1080。
NVIDIA + H.265 → ✓ hevc_nvenc @ RTX 4070 Ti SUPER · 零拷贝 · 60 帧 / 889 ms · 1598×1080
AMD    + H.265 → ✓ hevc_amf   @ Radeon 780M · 零拷贝 · 60 帧 / 786 ms · 1598×1080
切回 H.264     → CPU 行恢复可用（同一尺寸）
```

结果行现在会写出尺寸，因为"测的是哪一档"本身就是结论的一部分。

## 附：这一轮真正改变的一件事

V2.3 的失败模式是"打开成功 → 首帧死 → 整个导出死"。本轮把它变成"**打开成功不算数，编出第一帧
才算数**"。这不是给 `hevc_mf` 打补丁，是把"可用"的定义从 `avcodec_open2` 挪到了真正出画面那一步；
同一个改动顺带解释了为什么 Auto 在 HEVC 上会一路试到底而不再中途停住。
