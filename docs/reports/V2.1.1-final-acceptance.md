## A. CLI 混音回写

### A.1 真实调用链

```
openscreen export <proj> --out <mp4> --audio <wav> --audio-mode mix
  └─ CliExportRunner
       ├─ exportMultiNative(clips, outPath, sceneJson, params, inputPaths)   ← V2.1.1 新增第 5 参
       │    └─ IPC compositor.exportMulti
       │         ├─ planExportWrite(outPath, clips, { extraProtected: inputPaths })  ← 编码前
       │         ▸ 原生编码 → <out>.partial-<pid>-<uuid>.mp4
       │         └─ commitExportFile → rename 到 outPath
       ├─ fetch(outPath) + fetch(audioPath) → mixVoiceoverIntoVideo
       └─ writeExportToPath(bytes, outPath, inputPaths)
            ├─ planExportWrite(outPath, [], { extraProtected })   ← 同一条规则
            ├─ writeFile <partial> → commitExportFile
            └─ 失败 → discardExportFile
```

`inputPaths` 由 `exportedInputPaths(request, clips)` 一次算出（`src/cli/exportProject.ts`），
内容 = 每个 clip 的 `screenPath`/`webcamPath` + `audioPath` + `projectPath`；**导出自己刚生成的
中间成片不在名单里**（它是这一趟的产物，读回来再写回去是设计），写回阶段与编码阶段拿到的是
**同一份名单**。

### A.5 本轮修掉的一个真实缺陷（任务 A 发现）

**修复前**（`v211b` 构建，实测）：`--out` 指向配音文件时，第一遍原生导出只按 clips 校验，
**把配音覆盖成了刚渲染的视频**（`58a9d80b…` → `e5fe8901…`），拒绝发生在混音写回阶段——太晚。

**修复**：把 `inputPaths` 作为 `protectedPaths` 传进 `exportMulti`（契约 + 客户端 + 主进程），
与 clips 名单取并集，**编码前**判定。**修复后实测**：同一命令在 `v211e` 上被拒，
`voice-copy2.mp4` 哈希 `58a9d80b…`、大小 78,750,995 B **原样不动**。

## B. GUI 取消导出

### B.1 先摸清"取消到底在哪一层"——结论：MP4 **没有**取消

| 层 | 修复前的事实 |
|---|---|
| 对话框 | `disabled={isBusy && !(format === "gif" && phase === "rendering" && !cancelPending)}` ⇒ **MP4 渲染期间取消按钮是禁用的** |
| `handleCancel` | 只调 `cancelGifExportNative(job.id)`；MP4 没有 id（`id: format === "gif" ? uuid() : undefined`） |
| 主进程 | 只有 `gifExportJobs` 有取消；`exportMulti` 是一次 `AsyncTask`，无句柄 |
| 原生 | 只有 `create_gif_export_control` / `cancel_gif_export` |

⇒ 长导出期间用户唯一的出路是关窗口。这是**产品缺陷**，不是自动化能力问题。

### B.2 修复（最小、沿既有模式）

1. **原生**：`run_composited_multi` 增加 `cancel: Option<&dyn Fn() -> bool>`，在**逐帧回调**里检查；
   napi 增加 `createMp4ExportControl` / `cancelMp4Export`，复用已有的取消原语（`AtomicU8` 三态）。
   取消时**就地关闭 muxer**（`avio_closep` + `avformat_free_context`），否则 ffmpeg 句柄会把临时
   文件锁到进程退出（见 B.4）。三平台签名同形：Windows / macOS / Linux。
2. **主进程**：`exportMulti` 收到 `exportId` 时创建控制并登记 `activeExportCancels`；
   新增 `compositor.cancelExportMulti`；取消导致的错误映射为错误码 **`CANCELLED`**（不是失败）。
3. **渲染进程**：两种格式都发 `exportId`；取消按钮在 `phase === "rendering"` 时可用；
   关窗/卸载时也按格式取消对应任务。

### B.4 本轮修掉的第二个真实缺陷（GUI 取消第一版实测暴露）

第一版实现在取消后调 `discardExportFile`，Windows 回 **EBUSY**（ffmpeg 尚未松手）⇒ 异常冒泡，
把"用户取消"变成了"导出失败"：对话框显示 `EBUSY: resource busy or locked, unlink …`，
临时文件留到进程退出才可删（实测：app 关闭后同一条 `rm` 立刻成功）。

两处修复：

- `electron/exportPathGuard.ts`：`discardExportFile` 改为**best-effort 且绝不抛**，对
  `EBUSY/EPERM/EACCES` 做 0/30/60/120/240/480 ms 重试，仍失败只 `console.warn`；
  清理失败不该让用户的操作失败。
- `crates/compositor/src/pipeline_windows.rs`：取消点**就地关闭 muxer**。该文件原有的注释
  就写着"失败路径上 ffmpeg 上下文会泄漏，若某天失败成为常态再处理"——取消把它变成了常态。
