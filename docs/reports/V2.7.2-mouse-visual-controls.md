## 1. 本轮新增

**Rust 合成器**

- `scene.rs`：`SceneClickRipple` 增加 `dot` / `ring`（serde 默认 `true`）；新增 `SceneCursorTrail`
  （`lengthMs` / `opacity` / `thickness`）与 `SceneCursorAperture`（`radiusPx` / `opacity` / `color`），
  都挂在 `SceneCursor` 上，`#[serde(default)]` → 缺省即"不启用"。
- `frame_geometry.rs`：`CursorPlan` 增加 `trail: Option<CursorTrailLook>` 与 `apertures: Vec<LayerCB>`；
  `plan_cursor` 里轨迹参数接管采样窗口（长度 → `trail_from(t - length_ms)`，密度 2..24 随位移自适应），
  光圈生成一个 mode 4 的 disque；`click_ripple_cb` 多一个 `mask` 参数，写进 `src.xy`。
- 三后端（`compositor_windows/macos/linux`）：光圈先于波纹绘制（都在光标之下），轨迹的每个 tap 应用
  `alpha` 与尾端缩放。

**shader**

- `shaders.hlsl` / `shaders.metal`：mode 4 读 `src.x = 1 → src.y` 掩码（bit0 点、bit1 环、bit2 圆盘），
  `src.x = 0` 保持旧行为。
- `vk_shaders/layer.wgsl`：**补上了此前完全缺失的 mode 4 分支**（原来 mode 4 落在 `else` 的 mode 2 阴影里，
  Linux 上点击环会画成一块圆角矩形阴影）。这是 V2.7.1 起就存在的跨平台缺口，本轮修复。

**设置层**：`CursorRippleSettings` 加 `dot` / `ring`；新增 `CursorTrailSettings` / `CursorApertureSettings`
与 `SETTING_BOUNDS.trail*/aperture*`；`readCursorTrail` / `readCursorAperture` 与 `readCursorRipple` 同一套
逐字段校验；`editorSettings` 读写 `cursorTrail` / `cursorAperture`；`projectPersistence` 白名单放行；
`stylePresets*` 带上三个对象；`sceneDescription` 新增 `sceneCursorTrail` / `sceneCursorAperture`，关闭时
**不写键**。

**UI**：`CursorPane` 加"圆点 / 圆环"两个开关、轨迹组（开关 + 三个滑块）、光圈组（开关 + 颜色 + 两个滑块）；
文案 12 条 × 15 locales。

## 3. mode 4 / LayerCB 契约核对

历史报告里"128 字节"与"208 字节"的冲突，以源码为准：

- `frame_geometry.rs` 的 `LayerCB` 有测试 `assert_eq!(size_of::<LayerCB>(), 208)`，`trail_a` 的偏移断言是 128。
  **208 是当前值**；`frame_geometry.rs` 里出现的 "128 octets" 是 mode 15 段落的历史注释，说的是该模式
  引入时的大小，不代表今天。
- mode 4 是否读 `src`：HLSL（`shaders.hlsl:4010` 起）与 Metal（`shaders.metal:3621` 起）的分支**都不读
  `src`、不采样 `uv`**；VS 用 `src` 算出的 `uv` 在 mode 4 里没有任何消费者。`src.xy` 因此可以安全地承载
  掩码，`LayerCB` 布局不变。
- WGSL 原本没有 mode 4 分支（分支链 `mode < 1.5` 直接跳到 `> 4.5`），本轮补上，并加了 `src.x = 0` 的
  兼容语义，与另两处一致。

## 8. 效果局部图像分析（真实导出）

素材：`%TEMP%\os-v272\`，1920×1080 / 4 s 静止灰（`#202020` 铺满，padding/shadow/圆角全 0），
光标停在画面中心，1 s / 2 s / 3 s 分别为左 / 右 / 中点击。波纹设为**纯红、160 px、600 ms**，
这样"红像素"只可能是波纹（光标 sprite 是白的），dot 半径（0.34 R）与 ring 半径（0.72 R）也拉得开。

| 工程 | 配置 | 红像素 | 半径分布 |
|---|---|---|---|
| `v6-dot` | dot ✓ / ring ✗ | 587 px | 全部落在 r ≤ 20（0–20: 582），**20–40 区间为空** |
| `v6-ring` | dot ✗ / ring ✓ | 2442 px | 20–40: 1091，40–60: 1351，**中心 r<20 无实心块** |
| `v6-none` | 两者都 ✗ | **0 px** | — |
| `v6-halo` | 光圈 r=150 / 0.6 / 红 | 21713 px | 0–100 连续（80–100: 5706），边缘按 `smoothstep` 淡出 |

轨迹（同一段光标扫动，800 ms / 0.9 / 收尾 0.6）：

| 工程 | 墨迹包围盒宽度 |
|---|---|
| `v6-notrail`（关） | **74 px**（只有光标本体） |
| `v6-trail`（开） | **414 px**（拖尾沿轨迹铺开） |

旧工程对照（无 `cursorClickRipple`，默认 72 px 波纹）：

| 工程 | ink（r ≤ 140 窗口） | r > 30 的墨迹 |
|---|---|---|
| `v6-legacy`（旧规则） | 6052 px | 4462 |
| `v6-none`（显式全关） | 5438 px | 4462 |
| `v6-dot` | 6002 px | 4460 |
| `v6-ring` | 7840 px | 6864 |

读法：legacy 比 none 多 614 px（那就是默认的点 + 环）；dot 只往中心加墨；ring 只往 r>30 加墨
（+2402 px）；none 只剩光标。**四条互相对齐，说明掩码真的按位生效，而不是"看起来差不多"。**

## 9. 四组 GPU 导出

| 请求 | 实际编码器 | 零拷贝 | 结果 |
|---|---|---|---|
| `OPENSCREEN_EXPORT_ENCODER=h264_nvenc` | `h264_nvenc` | 是（D3D11 纹理） | **PASS**，240 帧 / 4 s |
| `OPENSCREEN_EXPORT_ENCODER=hevc_nvenc` | `hevc_nvenc` | 是 | **PASS** |
| `OPENSCREEN_EXPORT_ENCODER=h264_amf` | — | — | **BLOCKED**：`OPENSCREEN_EXPORT_ENCODER=h264_amf ne nomme aucun candidat de ce codec` |
| `OPENSCREEN_EXPORT_ENCODER=hevc_amf` | — | — | **BLOCKED**，同一句 |

不设 `OPENSCREEN_EXPORT_ENCODER` 时，Auto 直接选 `h264_nvenc`，日志里没有任何 `h264_amf` 的尝试记录。
`h264_amf` 确实在 `pipeline_windows.rs::candidates()` 的 H264 列表里，`EncoderChoice::Auto` 的
`plan_candidates` 也不过滤它——所以"候选表里没有"与"代码写的不一样"，**原因尚未定位**，本轮不猜。
AMD 780M 在本机是否被导出管线识别，同样没有证据。这属于 V2.7.3 第一条要查的事。

每次导出的 MP4 都完整解码过（`ffmpeg -v error -i … -f null -` 无输出），帧数与时长对齐 240 帧 / 4 s。
