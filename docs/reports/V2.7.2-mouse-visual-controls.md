## 2. Seek 偏差的根因：我的坐标算错了，产品没问题

`seekToClientX`（`V4Timeline.tsx:915`）是这么算的：

```ts
const el = canvasRef.current;                       // 内层「缩放后的时间线帧」
const r = el.getBoundingClientRect();
const pct = Math.min(1, Math.max(0, (clientX - r.left) / r.width));
const targetTime = pct * total;
```

实测几何（600 s 工程、真实窗口）：

| 元素 | left | width |
|---|---|---|
| `tlTracks`（外层容器） | **0** | **1203** |
| `tlCanvas`（产品实际测量的） | **20** | **1163** |

滚动容器 `scrollWidth = clientWidth = 1203`（不可滚动，全宽可见），`devicePixelRatio = 2`。

上一轮的脚本用 `tracks` 的矩形算坐标：`x = (60/600)×1203 = 120.3`，而产品实际读到的
`pct = (120.3 − 20)/1163 = 0.0862` → `51.7 s`。这与实测 **51.745** 完全吻合。
120 s 同理：`(240.6−20)/1163×600 = 113.8`，实测 **113.809**。

所以上一轮那个"固定偏差"不是时间映射缺陷，也不是解码延迟，是**我的 E2E 用错了矩形**。
按任务 A4 的判定：仅测试脚本错误 → 只改脚本，产品代码不动。

## 3. 修正后的标尺点击（真实鼠标事件）

坐标改成 `x = (t/total) × canvasWidth`，点在 `tlCanvas` 上（pointerdown 冒泡到 tracks 的 scrub 处理器）：

| 请求 | 播放头 | 误差 | 响应 |
|---|---|---|---|
| 0 s | 0.516 | +0.52 | 519 ms |
| 60 s | 60 | **0** | 531 ms |
| 120 s | 120 | **0** | 529 ms |
| 300 s | 300 | **0** | 517 ms |
| 590 s | 589.997 | **−0.003** | 541 ms |
| 599 s | 598.999 | **−0.001** | 525 ms |
| 300 s（重复） | 300 | 0 | 514 ms |
| 60 s（逆向复访） | 60 | 0 | 517 ms |

- 除 0 s 外，误差 ≤ **0.003 s**，远小于一帧（60 fps ≈ 16.7 ms）。
- 0 s 的 0.516 s 是**边界效应**：x 被 clamp 到 1 px，`1/1163×600 = 0.516`。点 0 像素不可行，
  这是取值下界，不是失准。
- 每步 0.5 s 的响应里包含我脚本里等待 UI 稳定的时间，不是 seek 本身耗时。

程序化 API 那条路本机走不通：这个构建没有暴露 `window.__osProjectStore`（`store: false`），
所以"方法一"只能退化为渲染结果读数，判据放在 §4 的点击误差上。

**产品代码零修改**，`seekToClientX`、缩放、滚动、Split/Trim/Speed/Motion 都没碰。

| 光圈：点 `#ef4444` | `#59b3ff` → **`#ef4444`** |

落盘（`proj_v272_gui.openscreen` 的 `legacyEditor`）：

```

cursorClickRipple.left.color  = "#ffffff"
```

## 6. 构建卫生（新增只读检查）

`scripts/check-build-hygiene.mjs` + `npm run build:hygiene`。它检查的正是这两轮踩到的东西：

1. `dist/index.html` 引用的每个 `assets/*` 都存在（指向被删 chunk 的 index.html 会白屏）；
2. 入口 chunk 里的 `./xxx.js` 动态 import 目标都存在（缺一个，点开才报错）；
3. `dist/assets/*.js` 里不得出现测试探针（白名单目前只有 `__cursorProbe`）；
4. 给出"磁盘上有多少 chunk、多少个从入口图不可达"（不可达的正是塞进 asar 的历史）；
5. 给了 `--asar` 就顺带扫 asar 里的同一批禁用串。

对交付包的实跑：

```
ok   index.html references 3 asset(s), all present
ok   entry chunks checked: 3, missing imports: 0
ok   chunks on disk: 116, not reachable from the entry graph: 2
ok   app.asar 47.7 MB, no forbidden strings: true
build hygiene: OK
```

一处自查：第一版把 `browser-shim-cursor-v1` 也列进了禁用串，结果三个 index chunk 全报 FAIL。
那是**产品代码**（浏览器 shim 的 localStorage key，随包发布是对的），不是测试残留 —— 已从白名单移除，
注释里写明了原因。宁可少报，也不要报假警。

## 7. 预览里的"红色"没有单独量化（本项 PARTIAL）

光圈颜色写成 `#ef4444` 且在重开后保持，但"预览里那颗环是红的"我没能量化到像素级：

- 默认 `opacity 0.25`，环叠在灰底上采样到的是 `(173,108,109)` 这类被稀释的色调；
- 把不透明度拉到 1.0 再比的尝试，两张截图**完全相同**（`changed_px = 0`）——大概率是 range 的
  `fill` 没有触发 React 的 onChange，而我没在那一轮继续深挖。

所以：**颜色值链路（UI → 磁盘 → 重开）是 PASS，颜色在预览像素上的呈现是 PARTIAL**。
按"全部完成"的字面标准，这一项算没验完。
