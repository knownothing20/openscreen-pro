## 3. GPU 编码稳定性 — **PARTIAL**

设置只写 `recording-settings.json`（GUI 与 CLI 读同一个 `AppSettingsStore`），设备用**稳定 PnP id**，
不用 LUID。每个用例是真实 CLI 导出，输出是 8 s / 480 帧 / 1494×1080。

| 模式 | 设备 | 结果 | 输出 | 实测 |
|---|---|---|---|---|
| NVIDIA H.264 | `id:PCI\VEN_10DE…` | PASS | `h264/avc1` 480 帧 3,373,097 B | 4.4 s · nvidia-smi 编码器占用峰值 **49%** |
| NVIDIA H.265 | 同上 | PASS | `hevc/hvc1` 480 帧 2,864,469 B | 4.4 s · nvidia-smi 峰值 >0 |
| AMD H.264 | `id:PCI\VEN_1002…` | **PARTIAL** | `h264/avc1` 9,156,130 B | 5.0 s（成功时）· 见下 |
| AMD H.265 | 同上 | **PARTIAL** | `hevc/hvc1` | 同上 |
| CPU H.264 | `cpu` | PASS | `h264/avc1` 1,760,023 B | 7.1 s（软件编码，明显更慢更小） |
| Auto | `auto` | PASS | `h264/avc1` **9,156,130 B（与 AMD 手选逐字节相同）** | 4.6 s |

**Auto 的等价字节就是证据**：只有同一个编码器 + 同一套码控才会产出完全相同的文件，
所以 Auto 在本机解析到 AMF（与 V2.2/V2.3 的"AMF 是第一候选"一致），不是 NVENC。

设备身份与不静默回退：
- 手填一个不存在的 PnP id → 导出在渲染前被拒：
  `The selected encoder device is not present on this machine (PCI\VEN_10DE\DEV_2705…)`，
  且**没有**产出文件。这条是偶然得到的（第一次矩阵我拼错了 `&`/`\` 分隔符），但正好证明了拒绝路径。
- AMD 手选失败时错误是 `send_frame: -1313558101`，**不会**降级到 NVENC 或 H.264 —— 与
  `EncoderChoice::Vendor(0x1002)` 的"手选不允许回退，必须大声失败"一致；Auto 才允许换候选。

### 3.1 AMD 的间歇失败（本轮唯一真实问题）

| 指标 | 值 |
|---|---|
| AMD 真实导出总次数 | **39**（8 s 工程，跨 1494 / 1598 / 1752 / 1920 四种输出宽度） |
| 失败次数 | **6**（15.4%） |
| 失败形态 | 100% 相同：`NativeBridgeRequestError: send_frame: -1313558101 (Unknown error occurred)` |
| 失败发生位置 | **第 0 帧**：失败日志里 `progress` 事件数 = 0 |
| 失败后旧文件 | 未创建/未被触碰 |
| 失败后残留 | 仅 44–48 字节的 `*.render-*.partial-<pid36>-<nonce>.mp4` 头部文件（可被 24 h 清理器归属） |
| 重试 | 一旦重试即成功（同一配置随后 10/10、8/8 成功） |
| 与尺寸的关系 | **无**：早期集中在 1494，但稳定 profile 下 1494 连续 10/10 成功；失败也出现在 1920 |
| 与连续性的关系 | **无累积退化**：1598 连续 8 次 0 失败，单次耗时 6.06–6.43 s 平稳 |
| 对照：NVIDIA | **13/13 成功，10 次连续输出 sha256 全同（3,373,097 B）** |

已排除的解释：不是宽度对齐（1598 = 8k+6 稳定成功）、不是累积资源（8 连发全过）、
不是尺寸上限（同一尺寸 10 连发全过）。最合理的解释是 **AMF 会话建立的首帧在驱动层偶发失败**，
而产品在 V2.3.1 之后每次导出会开**两个** AMF 会话（一次性 probe + 正式实例），第二个会话的失败率被放大。

为什么本轮不修：它发生在原生层、无法在 TS 侧消除，且不能在观察轮里对编码路径做未经长期验证的改动。
最小可行方案（下一轮，Rust ≤ 20 行 + 1 条测试）：**首帧 `send_frame` 失败时，对同一候选重建一次会话**；
只重试第 0 帧，天然不会重复写入已编码的帧。

## 6. FFmpeg 子进程生命周期 — **PASS（含一条实测边界）**

- 混音子进程由 `spawn(ffmpegPath, argv, {shell:false})` 启动，参数数组；中文/空格路径（`WorkBuddy AI` 目录）
  全程正常，没有 shell 拼接面。
- stdout/stderr 持续消费，只保留有上限的 stderr 尾部。
- 取消/失败：子进程 close 之后才清理 stage；取消不 commit（V2.6 Final Audit 的预取消修复在本轮基线里，
  `AbortSignal` 已 abort 时入口直接抛 `VoiceoverMixCancelled`）。
- **主进程被硬杀的实测**（V2.6 Final Audit，同一 HEAD，未重复消耗时间）：`TerminateProcess` 杀掉 Electron main 后，
  ffmpeg 子进程在 **≤1.5 s 内自行退出**（stderr 管道断开），partial 停止增长。
  **这不是保证**：产品没有 Job Object，属于观察到的行为。
- 本轮 AMD 失败留下的 44–48 B partial 是这条规则的直接后果：名字里带 pid，可被清理器归属。

## 15. 结论

**OpenScreen V2.6 STABILITY OBSERVATION = PARTIAL**（15 条完成标准里 14 条满足，唯一例外是 AMD AMF 的间歇首帧失败）。

**能不能进日常生产使用？**
- **用 NVIDIA（本机当前设置）**：可以。13/13 稳定、输出字节可复现、连续 5 次同会话导出内存趋平、
  取消/失败/清理全部通过、打包版与开发版逐字节一致。
- **用 Auto**：可以。Auto 在本机解析到 AMF，但 Auto 允许换候选，首帧失败会顺延，不会把失败抛给用户。
- **手选 AMD**：能用，但要接受约 15% 的导出会在第 0 帧失败，重试即成功。这是驱动层问题，
  产品行为是正确的（明确报错、不覆盖旧文件、不留成品、不留垃圾），只是不好看。

**下一轮最小动作（不建议现在扩范围）**：
1. AMF 首帧 `send_frame` 失败时对同一候选重建一次会话（Rust，≤20 行 + 1 条测试）。
