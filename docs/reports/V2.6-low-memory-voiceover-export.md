## 2. 旧 / 新调用链

### 2.1 现有混音语义表（先固定，再替换）

读的是 `src/lib/exporter/voiceoverMix.ts`（已删除，见下）与 `CliExportRunner` 的调用点，不是推测：

| 语义 | 旧实现（Web Audio + mediabunny） | 新实现（随包 ffmpeg） |
|---|---|---|
| `mix` | 底轨 × 0.4 + 配音 × 1.0，直接相加 | `volume=0.4` + `amix=normalize=0`，同样的算术 |
| `replace` | 只放配音，底轨完全不参与 | 只取 `[1:a]`，不引用 `[0:a]` |
| 原视频无音轨 | 解码抛错 → 静默退回"只有配音" | 探测到没有 Audio 流 → 只有配音（同语义） |
| 原视频音轨损坏 | 解码抛错 → **静默丢掉底轨** | **明确失败**（差异，见 §9） |
| 配音短于视频 | 后面是静音 | `apad` 补静音 |
| 配音长于视频 | 被 OfflineAudioContext 长度截断 | 补静音后 `-shortest`，以视频结束为准 |
| 偏移 | `start(max(0, offsetSec))` | `adelay=<ms>:all=1`，负值按 0 |
| 增益参数 | `originalGain` 默认 0.4，CLI 无开关 | 同（`DEFAULT_ORIGINAL_GAIN`） |
| 输出 | 48 kHz / 2 ch / AAC 192 kbit/s | 同 |
| 归一化 / 限幅 / 淡入淡出 / 声道平移 | **不支持** | **不支持**（不新增） |
| 最终长度 | 视频时间轴 | 视频时间轴 |

两条只记录、不改的事项：

1. **保存仍写应用管理副本**：`<userData>/projects/<project.id>.openscreen`，不覆盖你打开的外部 `.openscreen`。V2.5 已记录，本轮未改。
2. **`bitrate` AVOption 被拒 ≠ 码率失效**。真实赋值链是 `ExportParams.bit_rate → export_params.bit_rate → encoder ctx->bit_rate`
   （`crates/compositor-view-napi/src/lib.rs` 里 `p.bitrate.filter(|&b| b > 0).map(i64::from)`），
   `-1414549496` 只是 `av_opt_set_int("bitrate")` 在这个 ffmpeg 封装上不认这个 AVOption，**码率本身由 ctx 设置生效**。
   V2.5 报告里"`--quality` 的 bitrate 在本机是无效参数"措辞过重，按本轮核对更正为：**AVOption 无效，码率赋值有效**。
   本轮未改编码器、码率与画质档位。

### 2.2 新旧链路

```
旧：render stage ──fetch──> renderer ArrayBuffer(214 MB) ──Blob──> decodeAudioData(整段 PCM)
    ──OfflineAudioContext(整段渲染)──> BufferTarget(整片 MP4) ──IPC 结构化克隆(201 MB)──> main 写盘

新：render stage ─┐
     voiceover ──┼─> main：probe(2 次，只读头部) → spawn(ffmpeg-shared.exe, argv, shell:false)
     mixed stage ┘        → 视频流 copy，音频 amix/adelay/apad → 写 <mixed>.partial-<pid>-<nonce>.mp4
                          → close/退出码/文件大小检查 → rename 到 mixed stage
    → inspectMp4（文件句柄）→ 既有 commit（rename 到用户路径）
```

**不再经过 renderer 的数据**：整片 MP4、全部 PCM、以及两者的任何 IPC 克隆。
**复用的既有模块**：`exportPathGuard`（目标校验/commit/丢弃）、`mp4Inspect`（结构校验）、
`audioPeaks.resolveFfmpeg`（随包二进制定位，含 `OPENSCREEN_FFMPEG_PATH` 覆盖与"存在≠可执行"检查）、
`exportTransaction`（事务）、`exportTempSweep`（清理）。

`src/lib/exporter/voiceoverMix.ts` **已删除**：它唯一的调用者换成了新路径，桌面端与浏览器端都没有第二个用户。
不保留"失败后回退旧大内存实现"的分支——这正是任务书禁止的那条。

## 5. 失败与取消

| 场景 | 旧目标 SHA256 | 子进程 | 残留 |
|---|---|---|---|
| 配音不存在 | 不变（用例 6） | 在 probe 阶段就失败，未写盘 | 0 |
| 配音损坏 | 不变（用例 6） | probe 报 `Cannot read media` | 0 |
| 混音中途取消（服务层真实取消，30 min） | —（未到 commit） | 1152 ms 内被杀，`cancelled: true` | stage 与 partial **都不留** |
| 输出指向输入素材 | 不变（用例 7） | preflight 拒绝，未启动编码 | 0 |
| 混音产物不是可用 MP4 | 不 commit（事务测试） | — | 两个 stage 都清 |
| commit 失败 | 不变（既有用例） | — | 临时文件丢弃重试 |

**取消的实现**：`AbortController` → `SIGTERM` →（3 s 后仍在则）`SIGKILL`；
只杀自己 spawn 的子进程，没有任何"杀全部 ffmpeg"的路径；`close` 之后才清理文件（Windows 上文件还被持有时删不掉，
`discardExportFile` 已有 EBUSY/EPERM 重试）。

**竞争**：取消与完成只可能收敛到一种结果——`close` 先到就是成功，abort 先到就是取消并删产物；
不存在"先报取消、随后 commit"（commit 在事务的最后一步，且混音失败会直接抛出）。

## 9. 限制

**真实运行**：Windows 11 桌面、RTX 4070 Ti SUPER、63 GB 内存。8/16 GB 机器**未实测**，
因此只能说"内存占用不再是 4.6 GB"，不能宣称"8 GB 必然可用/不可用"。

**与旧实现的已知差异**（都记录，未掩盖）：

1. **原音轨存在但损坏**：旧实现静默丢掉底轨只留配音；新实现直接失败。这是有意的——静默丢一条音轨比失败更糟。
2. **容器布局**：旧的 mixed 用 mediabunny 的 `fastStart:"in-memory"`（moov 在前）；新的是 ffmpeg 默认（moov 在后）。
   两者都能被本应用与播放器读，`inspectMp4` 只要求 `ftyp` 在首、`moov` 存在。
3. **AAC 编码器不同**：Chromium 的 AAC vs ffmpeg 原生 AAC，因此 mixed 文件的音频字节不同（任务书允许）。
   视频流字节相同（§4.3）。
4. **`--audio-offset` 的取值**：旧实现 `Math.max(0, offset)`，新实现同样钳位到 0，负偏移等价于 0。

**只在服务层验证、没走 UI 的部分**：
GUI 没有配音入口（本轮不新增），所以"混音中途取消"是用**同一个生产函数 + 真实 ffmpeg 子进程**驱动的，
标注为"服务层真实取消"；GUI 的视频导出取消是既有能力，未用它冒充混音取消。

**未运行**：macOS / Linux（只做共享代码静态审查：`spawn`、`process.kill(pid,0)`、`path`、`fs.rename` 都是跨平台 API，
但未编译验证）；安装包在干净机器上的安装验收（NOT_RUN）；Intel QSV；8/16 GB 机器。
