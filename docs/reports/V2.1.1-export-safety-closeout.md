## 1. 每条导出入口的真实调用链

主进程里能写"最终视频文件"的地方只有三处，全部经由 `electron/exportPathGuard.ts` 的同一套规则。

| 导出入口 | 调用链 | 临时文件 | 原子提交 | 源文件保护 | 失败清理 |
|---|---|---|---|---|---|
| `nativeBridge` `compositor.exportMulti` | 渲染进程 `exportMultiNative` → IPC → `nativeBridge.ts:439` → `planExportWrite`(:448) → 原生 `compositorViewService.exportMulti`(:454，写临时路径) → `commitExportFile`(:480) | **是** | **是**（同目录 rename） | **是**，名单来自本次 payload 的 `clips[].screenPath/webcamPath` | **是**（编码抛错 :469、addon 缺失 :473、commit 失败由 `commitExportFile` 自行清理） |
| `nativeBridge` `compositor.exportGif` | `exportGifNative` → `nativeBridge.ts:483` → `planExportWrite`(:492) → `gifExportJobs.run`(:504) 或 `exportGif`(:517) → `commitExportFile`(:538) | **是** | **是** | **是**（同上） | **是**（:527 / :531，含取消） |
| `write-export-to-path` | `CliExportRunner.tsx:354` → IPC → `handlers.ts:4208` → `planExportWrite`(:4232，带 `extraProtected`) → `fs.writeFile`(临时) → `commitExportFile`(:4244) | **是** | **是** | **是**（V2.1.1 补齐，见 §2） | **是**（写入失败清理 temp；commit 失败由 `commitExportFile` 清理） |

**CLI 导出**不是一个独立入口：`openscreen export` 走的就是上面第 1 条（MP4）或第 2 条（GIF）；
只有在需要混入配音时才追加第 3 条（读回刚导出的文件 → 混音 → 写回同一路径）。本轮实测
（§4/§9）确认这三条都在真实运行中生效。

**其它写文件的 IPC 已逐个排除**（不是导出入口）：

- `finalizeRecordingFile`（`handlers.ts:510`）写的是**录屏**，路径由主进程用 `RECORDINGS_DIR` +
  净化后的文件名拼出，不接受用户路径；
- `exportDiagnosticFile`（`handlers.ts:1978`）写 `.json` 诊断包；
- `save-export-session` / session manifest 写的是 `.json` 状态；
- `pick-export-save-path` 只弹对话框，不写文件；
- `cliMain.ts:456` 的 `--json` 报告是 `.json`，已经自带 temp + rename。

## 2. 源文件保护覆盖范围（V2.1.1 的实质修复）

V2.1 的 `write-export-to-path` **没有源文件保护**：它调用 `planExportWrite(path, [])`，传的是空
数组 —— 那个入口没有 clips，也就"没有名单"。这是规则上唯一剩下的洞。

**补法不是凭空编一份名单，而是先弄清这条链到底读什么：**

```
CliExportRunner（CLI 混音第二遍）
  读：outPath（它自己刚导出的成片）、request.audioPath（配音）、以及 clips 指向的源素材
  写：outPath
```

于是：

- 受保护名单 = `clips.flatMap(c => [c.screenPath, c.webcamPath])` + `request.audioPath` +
  `request.projectPath`（`CliExportRunner.tsx:364`），**全部来自它刚用过的那份 clip 列表**；
- `outPath` 本身**不**进名单 —— 那是它自己的产物，读回来再写回去是这条链的设计；
- 名单以可选第三参数穿过 preload → IPC → `planExportWrite(..., { extraProtected })`，
  与 clips 推导出的名单**取并集**，不是替代。

至此，"源文件保护"对所有写视频的入口都成立，并且是同一份实现。

## 3. Windows 路径安全测试（真实文件系统，非 mock）

`electron/exportPathGuard.test.ts` 用 `fs.mkdtemp` 建真实目录。**V2.1 只比较路径字符串**，
本轮换成"问文件系统"：

`canonicalPath()` —— `fs.realpath` 逐级解析，目标是新文件时停在**最深的已存在祖先**再拼回尾部；
`fileIdentity()` —— `dev:ino`，硬链接唯一能被抓住的办法。

| 场景 | 结果 | 依据 |
|---|---|---|
| 相对路径 | 拒绝 | 扩展名/绝对路径检查 |
| 大小写不同（`Take.MP4` vs `take.mp4`） | **拒绝** | realpath 后统一小写 |
| `nested/..//source.mp4` | **拒绝** | realpath 归一化 |
| 硬链接（另一个名字，无路径关系） | **拒绝** | `dev:ino` 相同 |
| 符号链接指向源 | **拒绝**（本机无符号链接权限时跳过，硬链接已覆盖同一规则） | realpath |
| 不同路径指向同一文件 | **拒绝** | 上面两条 |
| 输出 = 源文件 | **拒绝** | 同上 |
| 输出 = 工程文件 | **拒绝** | 扩展名只允许 `.mp4`/`.gif` |
| 目标已存在 | **允许**，但只在临时文件完整后 rename 覆盖 | `commitExportFile` |
| 祖先是文件（`blocker/sub/out.mp4`） | **拒绝**，`"…" is not a directory.` | 逐级 stat |
| 父目录尚不存在（首次导出到新文件夹） | **允许** | 最deep的已存在祖先 + 尾部 |
| 无法解析（权限等非 ENOENT） | **拒绝**，`Could not resolve "…" (CODE).` | 不猜测 |

**"不能安全判断就拒绝"** 落在两处：路径解析出现非"不存在"的错误直接拒绝；祖先是文件则拒绝，
因为那种路径根本写不成，说它"没有东西可保护"是假话。

## 9. 打包版真实运行结果

`SAFE_DELETE_BULK_CONFIRM_REQUIRED count:50`），`dist/` 被清到一半 —— `index.html` 与全部 JS 已删。

`Renderer crashed`）。**这不是应用缺陷**：把 `dist/` 改名移开（改名不算批量删除）后重新构建，
同一个 exe 立刻正常。记录在此，避免下次把它当成产品 bug。

构建：`npx vite build` → `npx electron-builder --win --dir --config.npmRebuild=false
--config.directories.output=release/v211b-unpacked --publish never`
